## 2. 가장 중요한 결과

### 2.1 플랫폼이 달라도 예측값이 완전히 같았다

| 환경 | 플랫폼 | P-in-1 | P-out-1 | P-out-2 |
|---|---|---|---|---|
| 로컬 호스트 | macOS arm64 | 7.936 | 8.055 | 8.054 |
| 로컬 컨테이너 | linux/arm64 | 7.936 | 8.055 | 8.054 |
| 로컬 컨테이너 | linux/amd64 (QEMU) | 7.936 | 8.055 | 8.054 |
| **Cloud Run** | **linux/amd64 (gVisor)** | **7.936** | **8.055** | **8.054** |

probe 5개 전부 소수 3자리까지 일치하고 적용 범위 판정도 같았다. 해석 불가 SMILES 2개는 네 환경 모두 `status=error` 로, `predicted_pIC50` 필드 없이 돌아왔다.

사전 예상에서 "arm64→amd64 로 BLAS·부동소수 합산 순서가 달라져 어긋날 가능성을 배제하지 않는다"고 적었는데 어긋나지 않았다. 라이브러리 버전을 전부 고정한 것이 이유로 보인다 — 클라우드 런타임이 로컬 컨테이너와 동일했다:

```
python 3.12.14 · numpy 2.5.4 · scipy 1.18.1 · sklearn 1.9.1 · joblib 1.6.0 · rdkit 2026.09.1
```

### 2.2 Cloud Run 은 gVisor 샌드박스에서 돌고, 그게 느리다

`/model-info` 가 돌려준 런타임 플랫폼:

```
Linux-4.19.0-gvisor-x86_64-with-glibc2.36
```

gVisor 는 syscall 을 사용자 공간에서 가로채는 샌드박스다. 측정값이 그 비용을 보여준다:

| 항목 | 로컬 컨테이너 (arm64) | Cloud Run (amd64 gVisor) | 배수 |
|---|---|---|---|
| 모델 로딩 | 0.844 초 | **4.998 초** | **5.9배** |
| 서버 처리 p50 | 10.040 ms | **35.042 ms** | **3.5배** |
| 서버 처리 p95 | 13.208 ms | 45.494 ms | 3.4배 |

**원인을 gVisor 하나로 단정하지 않는다.** CPU 세대·클럭 차이(로컬은 Apple Silicon, Cloud Run 은 할당된 x86-64 1 vCPU), 플랫폼 차이(arm64→amd64), 컨테이너 이미지 당겨오기가 모두 섞여 있다. 분리 측정을 하지 않았으므로 기여도를 나누지 않는다. 말할 수 있는 것은 **같은 코드·같은 모델·같은 라이브러리 버전으로 클라우드가 3.5~5.9배 느렸다**는 사실이다.

모델 로딩이 특히 느린 것(5.9배)은 joblib 역직렬화가 파일 I/O 와 메모리 할당을 많이 하는 작업이라 샌드박스 비용이 더 드러난 것으로 추정한다. 추정이고 확인하지 않았다.

### C3 — 콜드 스타트 (2회 측정)

| 회차 | 리비전 | 첫 요청 왕복 | 모델 로딩 |

2회뿐이라 분포를 주장하지 않는다. 유휴 15분 뒤의 재콜드 스타트는 측정하지 않았다.

## 4. 사전 예상 대 실제 — 2개 틀렸다

측정 전에 `configs/serving_m6_cloud.json` 에 적어 두고 비교했다. 결과를 보고 예상을 고치지 않았다.

| 항목 | 사전 예상 | 실제 | 판정 |
|---|---|---|---|
| 로컬과 예측 일치 | 일치 예상 (어긋날 가능성 열어둠) | 5/5 일치 | 맞음 |
| 서버 처리 p50 | 10~40 ms | 35.042 ms | 범위 안 (상단) |
| 클라이언트 왕복 p50 | 30~150 ms | 50.019 ms | 범위 안 |
| **콜드 스타트 첫 요청** | **2~15 초** | **0.13 초** | **범위 밖 — 115배 빨랐다** |
| **클라우드 모델 로딩** | **0.5~3 초** | **4.998 초** | **범위 밖 — 1.7배 느렸다** |
| 과금 | $0 예상 | **미확인** | 확인 불가 |
| 이미지 push 시간 | 3~20 분 | 약 1 분 | 범위 밖 (압축 173MB) |

### 왜 틀렸나

**콜드 스타트(2~15초 → 0.13초)**: 제 예상 모델이 틀렸습니다. "클라이언트의 첫 요청이 컨테이너 시작을 기다린다"고 가정했는데, Cloud Run 은 시작 프로브로 컨테이너를 **먼저** 준비시킨 뒤 트래픽을 넘깁니다. 배포 직후의 첫 요청은 이미 준비된 인스턴스를 만났습니다. 진짜 콜드 스타트 비용(5초)은 로딩 시간 쪽에 나타났습니다.

**모델 로딩(0.5~3초 → 4.998초)**: 로컬 컨테이너 0.844초를 기준으로 범위를 잡았는데 gVisor 샌드박스 비용을 과소평가했습니다.

**이미지 push(3~20분 → 1분)**: 805MB 를 올린다고 가정했는데, 레지스트리에 저장되는 것은 **압축된 레이어 173.6MB** 였습니다.

## 5. 비용 — $0 으로 관측했으나 확정은 아니다

| 항목 | 값 |
|---|---|
| 결제 계정 | `018DAD-0BD504-B88375` 연결됨 (`billingEnabled: true`) |
| 이 실행이 보낸 요청 | 241건 (probe 10 + 오류 11 + 지연시간 220) |
| Cloud Logging 집계 | 최근 135건 읽음 — `200×127, 404×3, 413×1, 422×4` |
| Artifact Registry 저장 | **173.612 MB** (무료 0.5GB 안) |
| **과금 금액** | **$0** — 사용자가 2026-10-22 Cloud Console 비용 화면에서 확인 |

### 말할 수 있는 것

관측된 $0 은 사용량과 모순되지 않습니다. 요청 241건·`min-instances=0` 은 Cloud Run 무료 등급(요청 200만 · vCPU-초 180,000)에 한참 못 미치고, Artifact Registry 저장 173.6MB 도 무료 0.5GB 안입니다.

### 말할 수 없는 것

**"과금이 0 임을 확정했다"고 쓰지 않습니다.** 측정이 2026-10-21~22 에 있었고 Cloud Billing 반영에는 하루 이상 걸립니다. 같은 날 본 0 은 **"과금 없음"과 "아직 미반영"을 구분하지 못합니다.**

구분하는 방법은 비용 테이블에 **Cloud Run / Artifact Registry 항목이 행으로 나타나는지** 보는 것입니다:

- 행이 있고 금액이 0 → 반영됐고 무료 등급으로 처리됨. 0 을 신뢰할 수 있다
- 행이 아예 없음 → 아직 미반영. 하루 뒤 다시 봐야 한다

자원은 2026-10-22 에 모두 삭제했으므로 **금액이 늘어날 경로는 없습니다.** 따라서 이 불확실성은 "0 인가 아닌가"가 아니라 "0 을 지금 확정할 수 있는가"의 문제입니다.

산출물: `cost_confirmation.json`

AWS 단계에서는 공개 가격 API 에서 **1차 요율**을 받아 응답 SHA-256 까지 보존했습니다(`reports/serving_m6_20261021/cloud_cost_estimate.json`). GCP 는 가격 페이지 본문을 기계적으로 받지 못해(JS 렌더링) **무료 등급 수치를 2차 출처에 의존**했고 1차 출처로 검증하지 못했습니다. 또 과금 금액은 API 가 아니라 **사용자가 화면에서 읽은 값**입니다. 두 단계의 증거 수준이 다릅니다.

## 6. 겪은 일

### 6.1 AWS 가 계정 수준에서 막혔다

원래 AWS ECS Fargate 로 계획했고 비용 추정까지 1차 출처로 끝냈습니다. `aws login` 승인 단계에서 `Something went wrong / Contact AWS support / appeal system` 이 떴습니다. 권한 부족이 아니라 **인증 자체가 완료되지 않았고**, 교육용 계정(`user/student`)의 계정 수준 제한으로 보입니다. 우리가 풀 수 없는 문제라 Cloud Run 으로 전환했습니다. **AWS 에 자원을 하나도 만들지 않았습니다.**

### 6.2 내 스크립트 버그로 첫 실행이 중단됐다

설정의 키 이름이 `C1_parity_with_local` 인데 스크립트가 `C1_parity` 를 찾아 `KeyError` 로 멈췄습니다. C1~C3 는 이미 끝난 상태였고, 재실행하면 인스턴스가 떠 있어 **콜드 스타트가 더 이상 콜드가 아니게** 됩니다.

버린 값을 되살리는 대신 이렇게 처리했습니다: 1차 측정값(167ms / 5.047초)을 파일로 보존하고, 새 리비전을 배포해 **진짜 콜드 스타트를 다시** 만들고 재측정했습니다. 결과적으로 콜드 스타트를 2회 얻어 1회 측정보다 나아졌습니다. 1차 값은 `cloud_verification.json` 의 `C3_cold_start.prior_measurement` 에 들어 있습니다.

### 6.3 이미지 크기를 잘못 읽고 정정했다

`docker image inspect --format '{{.Size}}'` 가 amd64 이미지에서 173,608,921 을 돌려줘 "attestation manifest 값"이라고 추측했습니다. **틀렸습니다.** Artifact Registry 가 저장한 크기가 정확히 173.612MB 로 찍혀, 그 값이 **압축된 레이어 크기**임이 드러났습니다.

| 측정 방식 | arm64 | amd64 |
|---|---|---|
| 압축 해제 (`docker images`) | 829 MB | 805 MB |
| 압축 (레지스트리 저장) | — | 173.6 MB |

### 6.4 Dockerfile 변경의 안전성을 확인했다

Cloud Run 이 x86-64 만 받아 amd64 빌드가 필요했고, `FROM` 을 arm64 플랫폼 digest 에서 **manifest 인덱스 digest** 로 바꿨습니다. 바꾼 뒤 arm64 를 재빌드해 기존 이미지와 비교했습니다 — **RootFS 레이어 전부 동일, 크기 829,238,735 바이트 동일**. 이미지 ID 는 달랐고(buildx 가 붙이는 provenance attestation 이 빌드마다 바뀝니다), 그 사실을 숨기지 않습니다. 같다고 말할 수 있는 것은 레이어와 크기입니다.
