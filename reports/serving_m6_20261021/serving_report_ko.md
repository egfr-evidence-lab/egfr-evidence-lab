## 1. 이 보고서가 다루는 범위

M6 의 완료 증거는 세 개다. 이 실행으로 **첫 번째와 세 번째 일부**를 채웠다.

| 완료 증거 | 상태 | 근거 |
|---|---|---|
| 버전이 고정된 추론 API·컨테이너 | **충족** | `egfr-pilot22-inference:v1`, 베이스 이미지 digest 고정, 해시 3개 검증 |
| 실제 클라우드 요청·응답과 모델 버전 | **미충족** | AWS 세션 만료. 자원을 만들지 않았다 |
| 오류·로그·재시작·지연시간·비용 기록 | **부분 충족** | 오류·로그·재시작·지연시간은 측정했다. 비용은 **추정**뿐이고 실제 청구 기록이 없다 |

그래서 **M6 를 완료로 쓰지 않는다.** 아래 결과는 전부 노트북 1대(macOS Apple Silicon)와 그 위의 Docker Desktop VM 에서 나왔다.

이 분자들의 실제 EGFR 활성은 조회하지 않았고 주장하지 않는다. 모델이 입력에 반응하는지만 본 것이다.

## 3. 서비스 계약

```
GET  /healthz     프로세스 생존. 모델 상태와 무관
GET  /readyz      모델 로딩 + 해시 3개 일치 시 200, 아니면 503
GET  /model-info  모델·코호트·설정 해시, 학습 규모, 라벨 범위, 고지, 런타임 버전
POST /predict     SMILES 배열 → 분자별 예측·적용 범위 판정·고지
```

설계상 거부한 것:

- **학습·재학습 엔드포인트 없음.** 서비스는 추론만 한다 (`/train`·`/fit`·`/retrain` 모두 404 확인)
- **고지 생략 옵션 없음.** 2절의 결과가 이유다
- 예측값을 `measured` 나 `실측` 으로 부르는 필드명 없음. 성공 응답은 `value_is_a_prediction_not_a_measurement: true` 를 스스로 달고 나온다
- 변이형·세포 실험·분해제 지표 예측 안 함. 학습 라벨이 WT 생화학 IC50 뿐이다

모델을 다시 학습하지 않고 **M5 의 `ActivityPredictor` 를 그대로 호출**한다. 전처리와 적용 범위 판정을 서비스에서 다시 구현하면 두 경로의 출력이 갈라지기 때문이다.

| 항목 | 값 |
|---|---|
| 이미지 | `egfr-pilot22-inference:v1` · 829 MB · linux/arm64 |
| 베이스 이미지 | `python:3.12.14-slim-bookworm@sha256:eb5be8e5...0333` (digest 고정) |
| 모델 | `rf_pilot22.joblib` · SHA-256 `c6538d0d...9869` |
| 코호트 | SHA-256 `c0f5ed9e...655e9` (CHEMBL4258549) |
| 설정 | SHA-256 `29471fcc...5c2b7` |
| 직접 의존성 | `deployment/requirements-serve.txt` |
| 실제 설치 목록 | `deployment/requirements-serve.lock.txt` (**컨테이너 안에서** `pip freeze` 추출) |

베이스 이미지를 digest 로 고정한 이유: 태그는 같은 이름으로 내용이 바뀔 수 있고, 그러면 "다시 만들 수 있다"는 말이 성립하지 않는다.

macOS arm64 의 freeze 를 리눅스 컨테이너의 증거로 쓰지 않았다. lock 파일은 컨테이너 내부에서 뽑아 꺼냈다.

`.dockerignore` 는 **허용 목록 방식**이다. 전부 제외하고 서비스에 필요한 것만 되돌린다. 거부 목록으로 두면 새 폴더가 생길 때마다 빌드 컨텍스트에 조용히 섞인다. 이 저장소는 공개이고 `data/`(247MB)에 원자료가 있어 빠뜨리는 쪽이 더 위험하다. 이미지에 자격증명과 원자료를 넣지 않았다.

테스트: `tests/test_serving_app.py` 18개 신규. 저장소 전체 **81개 통과**(기존 63 + 신규 18).

## 7. 측정 중 겪은 일 — 포트 8000 이 다른 서비스였다

컨테이너를 `-p 8000:8000` 으로 띄웠는데 호스트에서 `127.0.0.1:8000/readyz` 가 "Not Found" HTML 을 돌려줬다. 컨테이너 내부 health check 는 200 이었다.

원인: **포트 8000 을 다른 프로세스(PID 43523)가 IPv4 로 이미 점유**하고 있었다. Docker 는 IPv6 로 바인딩했고, 그래서

- `127.0.0.1:8000` (IPv4) → 그 다른 프로세스
- `localhost:8000` (IPv6 로 해석) → 컨테이너

이 상태로 지연시간을 측정하면 **엉뚱한 서버를 재게 된다.** 포트를 `127.0.0.1:8010` 으로 옮겨 해결했고, 검증 스크립트가 측정 전에 `/model-info` 의 해시 3개를 확인하도록 해 같은 함정을 다시 밟지 않게 했다. 잘못된 대상을 측정하는 쪽이 측정에 실패하는 쪽보다 나쁘다.

## 9. 클라우드가 미충족인 이유

AWS 프로필 `skn33`(`ap-northeast-2`, `arn:aws:iam::498777149300:user/student`)이 설정돼 있지만 **세션이 만료**됐다.

```
aws: [ERROR]: Your session has expired. Please reauthenticate using 'aws login'.
```

권한 점검 스크립트(`scripts/check_cloud_access_m6.py`)를 만들어 뒀다. **읽기 전용 호출과 권한 시뮬레이션만 하고 자원을 만들지 않는다.** 배포를 바로 시도했다가 중간에 실패하면 어디까지 만들어졌는지 추적하기 어렵고 남은 자원이 과금된다. M4 에서 쓴 순서와 같다 — 가능한지 먼저 확인하고, 안 되면 안 되는 증거를 남긴다.

점검하는 동작 23개: ECR 생성·인증·업로드·삭제, ECS 클러스터·task definition·실행·조회·중지·삭제, `iam:PassRole`(Fargate 필수), CloudWatch 로그 그룹 생성·보존 기간 설정·수집·삭제, VPC·서브넷 조회, 보안 그룹 생성·규칙·삭제.

계정이 교육용(`user/student`)이라 `iam:PassRole` 이나 ECS 권한이 없을 가능성이 있다. 로그인 후 점검 결과를 보고 판단한다. 막히면 M4 처럼 차단 증거를 남기고 보류한다.

산출물: `cloud_access_check.json` (현재 `blocked_no_credentials`)

## 10. 주장하지 않는 것

- **"EGFR 활성 예측 서비스"가 아니다.** pilot22 — 22건·12 scaffold·단일 문헌·단일 assay 의 WT 생화학 IC50 범위다
- **이 모델이 쓸만하다고 주장하지 않는다.** M1 교차검증에서 평균 예측(Dummy)보다 낫다고 확정되지 않았고(3개 seed 모두 차이 구간이 0 포함), 2절에서 적용 범위 밖 상수 붕괴를 확인했다
- **"클라우드 배포 완료"가 아니다.** 컨테이너까지다
- **지연시간은 처리량이 아니다.** 순차 요청 1배치의 측정이다
- **비용은 추정이다.** 청구 기록이 없다
- 검증 전부가 노트북 1대에서 나왔다. 다른 기계에서 같은 수치가 나온다고 주장하지 않는다

## 11. 남은 일

1. `aws login --profile skn33` (사용자 직접 — 브라우저 인증)
2. `scripts/check_cloud_access_m6.py` 실행 → 권한 판정
3. 판정이 `ready` 면 **비용 승인을 받은 뒤** 배포·측정·정리
4. 막히면 차단 증거를 남기고 M6 클라우드 항목을 보류

자원을 만들기 전에 사용자 승인을 받는다. 만든 자원은 측정 후 삭제하고 삭제 사실을 기록한다.
